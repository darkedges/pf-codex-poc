# Local Vault tool credential custody

Implemented and verified on the selected Windows/Docker host, 2026-10-31 AEDT. This is persistent **local PoC custody**, not approval for a production deployment. Dedicated local credentials are now enrolled; see the [persistent backend milestone](persistent-tool-backend.md) for current state and non-destructive tests. The tool service remains stopped; no new public listener, Microsoft request, PF client change or Graph permission is involved.

## Trust and credentials

The existing TLS Vault at `https://localhost:9470` has a dedicated KV v2 mount `federated-copilot-tool-secrets`, with compare-and-set writes required and three retained versions. Its `runtime` record uses the closed six-field schema in `infra/tool-api/secret-record.schema.json`. No token audience or delegated identity is inferred from this record; the tool's independent issuer/JWKS and online grant checks remain required.

`tool-cert` authenticates the exact public certificate enrolled as `tool-runtime-renderer`. The renderer obtains only `tool-runtime-read`, without the default policy: read one `data/runtime` record, one token use, maximum 120 seconds. It has no list, write, delete, Transit, token creation or administration rights. The consent authority's sign-only credential cannot read tool secrets. This uses Vault's [certificate authentication method](https://developer.hashicorp.com/vault/docs/auth/cert).

The renderer certificate lasts 30 days. Its private key stays in the protected host directory `.local/tool-vault`; it is never mounted in the tool container. The directory and existing children are checked for reparse points and ACLs granting only the current Windows account and SYSTEM full control. Local account/SYSTEM compromise remains a PoC trust limitation. Docker Desktop bind mounts and host administrators are part of that trust boundary.

Only setup/enrollment scripts use the existing lab operator credential in memory. Rendering uses certificate authentication and does not load the operator bootstrap, authority signing lease or authority private key. No token is persisted by the renderer. Vault validates its own server certificate against the configured PF lab CA; no TLS verification bypass is supported.

## Commands and enrollment

- `npm run vault:tool-setup`: reconcile the dedicated mount, policy and certificate role, preserving any runtime record. A conflicting engine/auth mount fails. A missing renderer certificate/key pair is generated locally; a partial pair fails. This does not start or unseal Vault. Follow the existing Vault recovery runbook if needed.
- Prepare `.local/tool-vault/enrollment.json` privately using exactly the schema fields. Obtain the actual server SAN/certificate chain, caller CA, outbound CA and registered PDP workload signing key through their selected enrollment process. Generate a distinct 32-byte random audit HMAC key. Never put values in command arguments, chat, source control, logs or fixtures. Setup first creates/protects this directory; files must inherit its restricted ACL.
- `npm run vault:tool-store -- --expected-version 0`: initial enrollment only. For rotation, pass the exact current positive version. Invalid records or stale versions fail without overwriting the record. The operator entry file is deliberately not automatically deleted; securely remove it after confirming enrollment according to the host's credential handling procedure. Vault enrollment and verification share an exclusive custody lock.
- `npm run vault:tool-render`: authenticate, read the current version and validate all six fields before writing anything. It checks bounded strings, complete PEM values, RSA keys of at least 2048 bits, server key/certificate match, CA constraints and certificate dates with five minutes of remaining validity. It publishes a fresh six-file directory by staging and renaming beneath the protected custody directory. Only the version and generated snapshot directory name are printed. No partial directory is selected and no live mount is overwritten. Missing, denied, malformed, expired or unavailable credentials cause failure; there is no mock or cached-file fallback.

Select the resulting directory explicitly as `TOOL_SECRET_SOURCE` only after reviewing the runtime config and dependencies. The tool sees those six files read-only and has no Vault credential. Rendering does not start/restart the tool, update Compose, enroll workload identity or change PF client enablement. Existing snapshots do not get revoked by a failed refresh; the operator must drain/stop and replace the service when its credential is revoked. Never automatically select the newest directory or roll back to revoked credentials. Remove retired snapshots under an agreed retention procedure.

For renderer certificate rotation, drain rendering, revoke outstanding tokens through the operator, replace the protected certificate/key pair, rerun setup to enroll the new public leaf, and verify old-certificate rejection. Tokens already issued remain usable until consumed, revoked or expired; deleting a certificate role alone does not revoke them. Certificate rotation is an operator procedure, not automated hot reload. The current maximum residual token lifetime is 120 seconds.

## Evidence and limits

`npm run vault:tool-test` runs against the actual TLS Vault and refuses to run if a runtime record already exists. It holds an exclusive local custody lock, installs a temporary synthetic runtime record with CAS 0, checks certificate login and one-use restrictions, forbidden paths/operations, token revocation, missing/unregistered client certificates, authority signer isolation, stale CAS rejection, version advancement, and the actual standalone renderer. It verifies record ownership/content/version before deleting test metadata and removes its generated files. A cleanup fault retains the lock and requires review. An injected transport failure tests outage handling without sealing/stopping the shared authority Vault. This is not evidence of a real outage/restart exercise for the persistent tool.

Initial custody verification passed **22 live checks**, with its synthetic runtime record, both versions and rendered files removed. Subsequent dedicated local enrollment created the persistent runtime record and three operator-only maintenance records. Current non-destructive verification passes **8 enrolled-credential checks** and **14 persistent policy checks**; baseline **247** and production **283** tests pass. `vault:tool-test` intentionally refuses an existing runtime record; use `vault:tool-enrolled-test` in the current state. Offline tests cover malformed/extra/missing fields, mismatched/weak keys, expired certificates, missing records, wrong policies, malformed versions and no partial publication.

The persistent local PDP launcher and dedicated local certificate/workload enrollment are now implemented. Remaining activation gates include private Docker transport, delivered credential/mount acceptance, audit ownership/retention and a controlled canary. Production lifecycle/PKI, Microsoft secure-token-post, Copilot calling-workload authentication and Graph/SharePoint remain separate unverified gates.
