# Initial Threat Model and Production Gates

Relay preparation checkpoint (2026-10-31): interactive provider sign-in has one successful live result; that token alone grants no tool access. The [new relay core](copilot-tool-relay.md) requires an exact-token binding created internally from verified broker context and a separately enrolled caller credential. Local signed-token tests cover caller substitution, equivalent-user token substitution, prompt/body authority, full delegated identity continuity, concurrent/failed replay, short binding expiry, session-close cancellation, current revocation and policy/audit/dependency failure. Callback key possession is not Microsoft-tenant attestation; production caller credential custody, HTTP/TLS parsing, admission controls, connector trace secrecy, broker lifecycle wiring and distributed replay remain deployment gates. The connector draft's headers do not establish those capabilities.

## High-priority review questions

- What is the authoritative consent evidence for autonomous execution, and what does it allow the agent to do when the user is offline?
- Can current Copilot Studio Generic OAuth and Direct Line channel policies support the unattended token-post flow without an interactive user session?
- What are the maximum approved Microsoft data categories and the data residency/retention rules?
- Who can revoke a grant immediately? What happens to running jobs and cached Microsoft Graph responses?
- Is each partner's identity namespace immutable and unique across both PingFederate servers?

## Do not ship with

`DEMO_ONLY=true`; hardcoded sample principals/grants; local `.local` signing keys; unsigned internal requests; plaintext gateway communications; unauthenticated mock token endpoints; or a Copilot mode that silently bypasses user authentication.

Persistent local tool update (2026-10-31): explicit Vault-only policy bootstrap creates no fixture grant and rejects fixture/conflicting databases. Replay persists across an actual process restart, signing leases are independently revoked on shutdown, and role public keys are distinct/algorithm-pinned/private-parameter-free. Dedicated local credentials reside in four KV records; the tool reader is denied CA/backend/monitoring private records. Enrolled service credentials/config pass loader checks without activation. Shared Windows account/SYSTEM, exportable local CA, host controller operator access, Docker bind mounts, lease expiry/recovery and pending private transport/audit operations remain PoC trust boundaries; this is not production approval.

Verified pre/post PDP audit preserves human/actor/org/grant/mode/audience/resource; wrong sender/proof/resource inputs fail, real expired tokens fail while grants remain active, fresh replacements work, and owner revocation blocks token use/new issuance. ## Repeatable session threats and controls - 2026-11-02

The opt-in repeatable profile must not turn a spent test into unlimited execution. A separate immutable reviewed deployment cap/window and per-consent slot counters survive restarts; one serial SQLite reservation prevents cross-browser/controller overspend. Every slot requires a new cryptographically verified human proof and explicit consent, and only independently confirmed revocation/recovery releases the next slot. Failed/lost consent responses retain ownership and block progression; absence of a visible commit is not proof of absence. Unknown scopes/resources/actors, stale proofs, replayed events and conflicting grant identity still fail closed. A presentation-only availability message cannot renew dependency health or lease expiry. Approved pin refreshes remain exact; no token-supplied issuer/key URL or automatic unknown-key trust is added. Recovered metadata may be cleared after one day while spent counters and unresolved recovery remain. Earlier one-shot evidence is neither migrated nor reset. Live repeatable acceptance, production process isolation and Microsoft tool trace protection remain UNVERIFIED.
