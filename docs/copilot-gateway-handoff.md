# Internal gateway proof handoff verifier

`GatewayProofHandoff` in `src/copilot/relay-handoff.ts` verifies an internal gateway's RS256 assertion with a configured issuer, dedicated audience, public key and key ID. The assertion is valid for at most 60 seconds and binds the exact request bytes through `body_sha256`. Embedded/remote key selection is rejected. Its JTI must be atomically reserved by an explicitly supplied replay store before proof processing; there is no default or process-memory fallback.

The strict body contains only brokerToken, agentToken and login (idToken/nonce). Independent verifier dependencies must authenticate the broker, agent and human evidence. Agent issuer/subject must match broker act; human issuer/audience/subject must match the configured login trust and broker sub. Current broker policy must permit the operation. Registration expiry is the earliest gateway, broker, agent, human or 120-second deadline. Caller-selected grant, scope, organisation, identity and resource fields are rejected.

This component does not receive an agent private key and does not sign agent evidence. It is an internal control-plane verifier, not a public tool endpoint or deployed HTTP registration route. Root composition must supply mature JOSE agent/broker/OIDC verifiers, a durable replay store and transactional custody implementation. The unit tests use a real signed gateway assertion and injected proof-verifier contracts; they do not establish a live gateway handoff.

The accept callback must commit only while cancellation is live. Its corresponding discard operation must atomically invalidate the exact provisional broker registration, including a cancellation tombstone so late work cannot commit after cleanup. Audit failure or timeout calls discard; neither a best-effort rollback nor an ignored AbortSignal is sufficient for deployment. These storage/cancellation properties remain an integration gate, not something the interface can prove for arbitrary callbacks. Replay reservations remain consumed on failure.

Nine focused tests cover successful signed/body-bound handoff, body substitution, concurrent replay, wrong agent/human, policy denial, untrusted key headers, unexpected fields, expired assertions and completion-audit cleanup. No real proof, external agent key or secret is in the test fixtures. No listener, production registration store or Microsoft conversation was created. The deployment review remains disabled until the real persistence/issuer composition and private transport are integrated and verified.


## Durable custody implementation (31 October 2026)

`RelayProofStore` now supplies a dedicated SQLite implementation. Replay reservations are issuer-qualified SHA-256 references, atomically reserved under `BEGIN IMMEDIATE` with FULL synchronization. Broker-token fingerprints key encrypted proof rows. AES-256-GCM uses a caller-supplied 32-byte secret-manager key, fresh nonce and authenticated schema/fingerprint/expiry; neither proof nor identity metadata is plaintext in the database. Records and replay reservations have separate bounded capacities and expire on subsequent maintenance operations. Ciphertext can remain on disk until that operation; this is not scheduled retention or cryptographic erasure.

Handoff `accept` now stages unusable proof; a required synchronous `commit` activates it only after completion audit. Abort is set before failure cleanup. `discard` erases ciphertext and leaves a five-minute cancellation marker, preventing a delayed insertion; every insertion and activation also checks cancellation. Successful retrieval atomically consumes and removes ciphertext before decrypting. Failure, wrong key or corruption cannot restore that entry. An audit success records the pre-commit verification checkpoint; a following commit failure is denied and discarded.

Composition must bind store methods explicitly: asynchronous wrappers for `reserveReplay`, `accept` and `discard`, and a directly bound synchronous `commit`. The store is an internal custody primitive, not an issuer: consumers must independently reverify every retrieved broker/agent/human proof and current policy before issuance. No private external-agent key is accepted. Existing in-memory issuer composition has not yet been replaced.

The parent directory must already have operator-controlled Windows owner/SYSTEM permissions; mode 0600 alone does not enforce Windows ACLs. Canonical paths, regular single-link database/sidecar files and no symlink parents are checked at opening. This assumes a trusted local filesystem and account; it does not defend against an operator swapping files, database rollback or clock rollback. Dedicated Vault key enrollment, runtime/controller integration, separate-process crash tests and live gateway transport remain UNVERIFIED. The store currently uses Node's experimental built-in SQLite API. No runtime database/key, public route or Microsoft test was created by this milestone.


## Vault-backed issuer composition (31 October 2026)

`openDurableRelayAuthority` composes the gateway verifier, durable custody and `DurableRelayIssuer` using the same explicit broker/agent/OIDC verifiers and current policy dependencies. It obtains the encryption key only through the fixed `fetchCustodyKey` reader; no environment/plaintext-file/mock fallback exists in this composition. The caller supplies a pinned TLS/mTLS Vault transport. Key buffers are wiped after the store copies them, and closing the composition aborts active issuer work and closes custody. Stop incoming registration work before closing the composition; shutdown/drain wiring into the persistent controller is still pending.

The new issuer consumes the exact stored proof once, compares fresh verified broker claims with the retained snapshot and relay context, revalidates signed agent evidence and the human login, and checks current policy before and after exchange. The exchange dependency receives the retained agent JWT and human proof, never a private agent key. It must implement the actual authority/PF exchange; the resulting tool token is still independently verified by ProviderToolRelay. Wrong human/actor/grant/context, autonomous mode, revoked policy, expiry, cancellation and late exchange completion fail closed. Consumed broker fingerprints remain blocked for five minutes, covering the admitted broker's maximum lifetime even when the shorter handoff deadline passes.

`npm run relay:custody-enroll` previews local Vault enrollment; append `-- --enroll` to enroll or reconcile. The dedicated record is `federated-copilot-tool-secrets/relay-proof-key`, schema version 1, purpose `relay-proof-encryption`. The cert-auth role `copilot-relay-custody-reader` grants only policy `copilot-relay-custody-read`: one read, no default policy, at most 120 seconds. It reuses the enrolled relay renderer certificate as the same local workload identity; policy separation is not OS/process isolation. No existing runtime/connector reader policy is widened. The operator enrollment command creates the key with CAS 0 and refuses to overwrite it or foreign role/policy definitions. Partial enrollment may leave the dedicated key/role in place; rerunning reconciles those resources, preserving the key. Automatic key rotation is deliberately unsupported because replacing the key would strand existing ciphertext.

## Actual retained-agent exchange verification (31 October 2026)

`RetainedProofExchange` now implements the interactive custody-to-PF callback. It forwards the retained agent JWT and human ID-token/nonce to the separately authenticated authority request, derives the grant and operation from verified broker claims, and independently verifies the returned authority assertion. It checks the configured issuer/audience, complete human/actor/org/grant/mode/scope binding, operation, resource and bounded lifetime before contacting PF A. A separate gateway OAuth client signs a fresh RS256 private-key JWT; the external agent JWT is forwarded unchanged as actor evidence. No issuance POST is retried. The fixed PF A result is independently verified, then the existing Gateway 2 exchange obtains and verifies the PF B tool token. Every boundary compares the original delegated identity. A bounded deadline/cancellation suppresses subsequent sends and late results; already-started authority/PF B work retains its own transport deadline and cannot be undone.

| Boundary | Fixed local endpoint / audience |
|---|---|
| Current policy / authority | `https://localhost:9452/v1/assertions`, separately authenticated `policy-agent` workload; authority assertion audience `api://pf-a/consent-proof` |
| PF A exchange | `https://localhost:9033/as/token.oauth2`; resource `urn:copilot:consent:gateway-2`; resulting audience `api://gateway-2` |
| PF B tool exchange | `https://localhost:9034/as/token.oauth2`; resource `urn:copilot:delegated:tool`; resulting audience `api://copilot-tool` |
| Private tool | `https://tool-api:8443/v1/tools/verify-access`, fixed empty-body capability, independent mTLS and current PDP |

The local composition is `scripts/pf/retained-relay-exchange.ts`. It loads authority verification keys from the selected Vault Transit public trust and public agent JWKS. It reads only the gateway OAuth and policy workload private credentials needed for those separate clients; it never loads or signs with the external agent private key. These local workload credential files still need dedicated production Vault loading and workload isolation before permanent hosting.

The bounded `relay:real-test` harness now uses `openDurableRelayAuthority`, the actual limited Vault custody-key reader and encrypted SQLite store, real signed gateway envelope, independent mature JOSE verification, the real authority/PF A/PF B chain and private Docker tool. ### OIDC signing-key reconciliation

Initial actual runs stopped before consent because fresh local PF ID tokens used an RSA key ID outside the existing explicit OIDC pins. It rejects wrong issuer/JWKS, private key material in candidate signing keys, weak RSA, duplicate IDs and disallowed signing algorithms. This is an explicit local trust reconciliation, not automatic acceptance of a JWT-selected key or a production rotation service. The private controller was stopped and restarted to load the updated trust; existing grants and tool runtime trust were preserved. No PF signing configuration changed. Review receipt: `.local/pingfederate/oidc-key-review-d167c716-909c-46d8-b2e9-d950d23744fc.json`.

Ping documents dynamic key publication and rotation in [Configuring dynamic signing keys](https://docs.pingidentity.com/pingfederate/13.0/administrators_reference_guide/pf_config_dynamic_signing_keys.html). The bounded allowlist still needs an operational key-retirement/rotation procedure; automatic widening and clock relaxation remain disabled.

## Private gateway HTTP transport (31 October 2026)

`src/copilot/relay-handoff-http.ts` now provides `createGatewayHandoffServer` and `createGatewayHandoffClient`. Both are explicit factories: neither opens a listener, enrolls a certificate nor selects an endpoint from request data. The control-plane route is **POST `/v1/internal/relay/proofs`**. It must remain private and separate from `/v1/copilot-tools/verify-access`; never add it to the public Cloudflare ingress.

The server requires CA-validated mutual TLS and one exact configured gateway certificate SHA-256 fingerprint. The same selected gateway's RS256 signing key, issuer and dedicated audience are independently pinned by GatewayProofHandoff. The single `Authorization: Gateway <assertion>` binds the exact UTF-8 JSON bytes through `body_sha256`; method/path are fixed by the server and the dedicated assertion audience. The body remains only brokerToken, agentToken and login.idToken/nonce. No header, query or body override supplies subject, actor, grant, scope or resource. TLS client identity cannot be substituted by a forwarded certificate header. The transport rejects duplicate credentials, excess header pairs, unknown paths/queries, wrong media type, content encoding, malformed UTF-8 and bodies above 40,000 bytes before proof processing. It enforces explicit connection, concurrency, rate, header/body and total-operation limits. Telemetry projects only the fixed event name and HTTP status.

Success is HTTP 201 with exactly `{registered:true, expiresAt}`; errors project only generic binding/availability/request categories. The client uses a fixed configured HTTPS origin/path, CA and hostname validation plus an exact server certificate fingerprint, its own mTLS credential, a fresh signed envelope and no redirects or automatic retries. It bounds and validates the response, including expiry. Neither side logs requests, proof values, authorization headers, cookies, credentials or response bodies.

Request abort, client disconnect and `beginDrain()` propagate cancellation into GatewayProofHandoff. The handoff's external signal is checked before work, between verification/policy/storage steps and immediately before synchronous activation. `shutdown()` stops admission, cancels active work, closes connections/listening and waits for HTTP handlers before custody can be closed. The composition root must call this shutdown before closing durable authority. A further failing-first regression exposed a lost-event race if a dependency synchronously cancelled before the deadline promise installed its listener; handoff, durable issuer and retained exchange now explicitly reject an already-aborted controller when installing their deadline race. No timeout or clock checks were weakened.

HTTP delivery and a database commit cannot be atomic. If a connection is lost after activation but before the client receives HTTP 201, the registration may exist until its short expiry. Do not automatically replay that proof; retries with the same broker token are denied and can cancel its registration. Persistent-controller ownership, operational reconciliation of uncertain outcomes and credential/certificate rotation remain integration work. Clearing proof fields is best-effort memory hygiene, not guaranteed erasure of immutable JavaScript strings.

## Managed provider-binding mode

The managed PoC selects a mandatory bindProvider/invalidateProvider dependency pair. In that mode the signed private body contains exactly brokerToken, agentToken, login and providerToken; the original three-field mode remains isolated for existing consumers. Independent broker/agent/human checks and online policy precede provider binding. The provider verifier and fixed issuer-qualified identity registry must accept the exact provider JWT; registration expiry also respects the resulting binding deadline. Any subsequent staging, audit, cancellation or activation failure invalidates the provisional provider binding as well as encrypted proof custody. The provider token never creates delegated authority by itself. The running application supplies both callbacks, while old/mock consumers cannot silently enable that mode.

See [the concrete Microsoft activation review](microsoft-tool-test-review.md) for the current managed service, credential roles, diagnosed one-second verified not-before alignment, local evidence and exact proposed public scope. The Microsoft setup has not yet been applied.
